# Додаткова специфікація 01: зв'язки N:M без сполучних таблиць

**Дата створення**: 2026-10-05

**Статус**: Прийнято

**Розбіжність**: Помилка 1 в `ai/audit.md` («сполучна таблиця замість зв'язку N:M»)

**Промпт**: `ai/04-prompt.md` (перегенерація `spec.md` і `erDiagram.mmd`)

**Доповнює**: `spec.md` (розділи 2, 3, 5), `erDiagram.mmd`, `adr/0001-nm-relationships-without-junction-table.md`, `adr/0002-report-as-self-relationship.md`

## 1. Проблема

Лабораторна вимагає: «чистий багато-до-багатьох — це зв'язок між сутностями; асоціативна сутність — лише коли зв'язок несе власні атрибути». У попередній версії:

- `spec.md` (5.7.1) і `erDiagram.mmd` містили `shared_uma_factors(shared_uma_id, factor_id)` без власних атрибутів;
- додаткова специфікація скарг вводила сутність `Report(reporter_id, reported_id)`, також без власних атрибутів.

Обидва випадки — це N:M, записані як сутності.

## 2. Зміни

| Було                                               | Стало                                                                |
| -------------------------------------------------- | -------------------------------------------------------------------- |
| Сутність `shared_uma_factors` з двома FK           | Зв'язок `SharedUma }o--o{ Factor : "має"`; сутності немає            |
| Сутність `Report` з двома FK                       | Самозв'язок `Player }o--o{ Player : "скаржиться на"`; сутності немає |
| Складений PK у `shared_uma_factors` (припущення 7) | Припущення знято: у моделі немає сутності, якій потрібен PK          |

## 3. Нові критерії

- **AC-02** (у `spec.md`): сполучних таблиць у моделі немає; асоціативна сутність допустима лише для зв'язку з власними атрибутами.
- Якщо скарга отримає власні атрибути (час, причина), `Report` стає асоціативною сутністю: це окреме рішення з оновленням spec і ADR-0002.

## 4. Критерії приймання

- У `erDiagram.mmd` немає сутностей без власних доменних атрибутів, окрім зв'язків N:M.
- Рендер показує дві лінії `}o--o{`: SharedUma–Factor і Player–Player.
