# Звіт про промпт: створення набору ADR для проєкту Umasearch

**Модель**: Claude Sonnet 5.5 (Anthropic)

---

## 1. Повний текст промпту

```text
На основі готового spec.md файлу проекту та мого шаблону ADR створи набір окремих ADR-файлів (Architecture Decision Records). Відповідай українською, технічні терміни та назви сутностей залишай англійською, як у spec.md.

Вхід

1. Специфікація: прочитай її повністю перед роботою.
2. Мій темплейт ADR: прочитай його повністю.

Як працювати з темплейтом

- Збережи структуру темплейту без змін: ті самі розділи, той самий порядок, ті самі назви заголовків, ту саму мову та формат метаданих (статус, дата, автори тощо).
- Не додавай розділів, яких немає в темплейті, і не пропускай наявні. Якщо розділ неможливо заповнити на основі spec.md, напиши в ньому `[NEEDS CLARIFICATION: що саме не вистачає]`.
- Усі поля-плейсхолдери замінюй реальним змістом.

Які рішення оформити

Сам визнач із spec.md перелік архітектурних рішень, які справді треба прийняти, і створи по одному ADR на кожне рішення. Рекомендовано 3-5 файлів. Орієнтовні теми (залиш тільки ті, що обґрунтовані spec.md, і додай інші, якщо вони випливають зі spec.md)

Вимоги до змісту кожного ADR

- Контекст: що змушує приймати рішення. Обов'язково посилайся на конкретні ідентифікатори зі spec.md (FR-xxx, BR-xxx, SC-xxx, розділи, сутності).
- Варіанти: щонайменше 2–3 реальні альтернативи з коротким списком плюсів і мінусів кожної щодо вимог spec.md.
- Рішення: обери один варіант і поясни чому, посилаючись на вимоги зі spec.md.
- Наслідки: позитивні, негативні, ризики, що змінюється в моделі даних чи в наступних кроках.
- Не суперечь spec.md і не змінюй прийняті там рішення (ліміти, діапазони, пороги, ролі).
- Spec технологічно нейтральний, тому конкретний стек (мова, фреймворк, СУБД) обирай лише там, де без цього не можна прийняти рішення, і обґрунтовуй вибір. Якщо вхідних даних недостатньо для вибору, залиш статус «Запропоновано» (або відповідний статус із темплейту) і познач `[NEEDS CLARIFICATION]`.
- Нічого не вигадуй поза spec.md: вимоги, числа та обмеження бери тільки звідти.
- Кожен ADR повинен описувати рівно одне рішення. Не змішуй кілька рішень в одному файлі.

Файли та іменування
- Файли повинні бути у форматі Markdown
- Імена файлів: `NNNN-короткий-заголовок-латиницею.md` (нумерація з 0001, kebab-case), якщо темплейт не задає іншого.
- Якщо одне рішення залежить від іншого або замінює його, вкажи це в обох ADR (посиланнями на номери).

Перевірка перед завершенням

- Кожен ADR відповідає структурі темплейту.
- Кожен ADR має посилання на вимоги зі spec.md та щонайменше 2 розглянуті варіанти.
- Немає суперечностей зі spec.md і між самими ADR.
- Немає двох ADR про одне й те саме рішення.
- Індекс у README.md збігається з наявними файлами.
```

## 2. Що видав ШІ

Створено чотири ADR-файли з індексом та залежностями між рішеннями:

| №    | Рішення                                                                  |
| ---- | ------------------------------------------------------------------------ |
| 0001 | Реляційна СУБД (PostgreSQL) як основне сховище даних                     |
| 0002 | Виконання пошуку, сортування та пагінації SQL-запитами в БД              |
| 0003 | Серверні сесії з cookie та рольова авторизація на сервері                |
| 0004 | Таблиця Report і атомарне оновлення `reports_count` та статусу `flagged` |

Кожен ADR містить 3 варіанти з плюсами й мінусами, посилання на FR/BR/SC/розділи spec.md, наслідки та посилання на залежні ADR.
