# ADR-0008: Повернення зі `flagged` не скидає `reports_count`

**Status**: Proposed

**Date**: 2026-10-22

---

## Context

ADM-04 (v1) вимагав, щоб при поверненні Player зі `flagged` Admin вибрав `unverified` або `verified`, а система скинула `reports_count` у 0. Це суперечить AC-03 (`reports_count` відображає кількість збережених скарг) і не узгоджується з AC-12: пара «скаржник — відповідач» унікальна, тож ті самі п'ять скаржників не можуть поскаржитися знову, а таблиця скарг лишається з п'ятьма парами при лічильнику 0. До того ж `flagged` перезаписує попередній статус (REP-03: «незалежно від попереднього статусу»), тому Admin мусить вибирати новий статус сам. Скидання лічильника — «припущення 1» у `spec.md` Завдання 1, не підтверджене.

## Decision Drivers

- Узгодженість з AC-03 і AC-12: `reports_count` = кількості збережених пар.
- Мінімальна зміна вимог (не вигадувати нових сутностей без ER).
- Тестованість: поведінка однозначна для REP-03 і ADM-04.

## Considered Options

1. Скидати `reports_count` у 0 (v1).
2. Не скидати `reports_count`; Admin лише вибирає статус `unverified`/`verified`.
3. Винести `flagged` в окремий прапорець, не пов'язаний з `verification_status`, і не скидати лічильник.
4. Дозволити повторні скарги після повернення (скинути пари).

## Decision Outcome

Chosen option: **Option 2**, тому що зберігає інваріант `reports_count` = кількість пар (AC-03), не потребує нових полів і не змінює унікальність пари (AC-12). ADM-04 переписано: система вимагає вибір статусу, встановлює його, **не змінює** `reports_count`, повертає записи до видачі. REP-03 переписано: `flagged` встановлюється, коли скарга доводить `reports_count` до значення ≥ 5.

## Consequences

### Positive

- Немає розбіжності між лічильником і таблицею скарг.
- Сценарії SC-050/051/055 однозначні; позначка `[NEEDS CLARIFICATION]` знята.

### Negative and risks

- Повернутий Player має `reports_count ≥ 5`: будь-яка нова скарга від нового скаржника знову виставляє `flagged` (SC-055).
- Admin, який повертає Player, не очищає причину `flagged`; потрібен процес поза системою.
- Рішення потребує підтвердження (спирається на припущення, а не на вхідні документи).

### Follow-up actions

- [ ] Звірити з ER: чи `flagged` — значення `verification_status`, чи окремий прапорець (Option 3).
- [ ] Підтвердити рішення; змінити статус на Accepted або повернутися до Option 3.

## Pros and Cons of the Options

### Option A

Скидати `reports_count`.

- Pros: Player одразу «чистий».
- Cons: порушує AC-03; лічильник розходиться з таблицею скарг.

### Option B

Не скидати.

- Pros: інваріант зберігається; мінімальні зміни.
- Cons: повернутий Player легко знову стає `flagged`.

### Option C

Окремий прапорець `flagged`.

- Pros: верифікація не втрачається при `flagged`; Admin не мусить вибирати статус.
- Cons: змінює модель даних (Завдання 1); без ER не перевірити.

### Option D

Повторні скарги після повернення.

- Pros: скарги можуть підтверджуватися наново.
- Cons: суперечить AC-12 (одна скарга на гравця); потребує видалення пар.
