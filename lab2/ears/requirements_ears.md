# EARS-вимоги: Umasearch (v2)

Позначка ✱ — припущення, якого немає у вхідних документах. Кожна ✱ має сценарій із тегом `@assumption` (LAC-02). Назви полів (`verification_status`, `rank_id` тощо) взято зі сценаріїв; з ER не звірено (`spec.md`, розд. 6, п. 4). Усього 37 вимог; ✱ — 15.

## 1. Облікові записи

| ID | Вимога |
| --- | --- |
| AUTH-01 | WHEN Guest подає реєстрацію, що відповідає AUTH-04.1–04.3, система SHALL створити Player з `verification_status = unverified`, `reports_count = 0`, `role = player`. |
| AUTH-02.1 | WHEN подано email і password існуючого запису, система SHALL автентифікувати користувача. |
| AUTH-02.2a | Система SHALL NOT приймати для входу ідентифікатори, окрім email і password. |
| AUTH-02.2b | Система SHALL NOT надавати відновлення пароля. |
| AUTH-02.3 ✱ | IF пара email + password не збігається, THEN система SHALL відхилити вхід, не вказуючи, яке поле хибне. |
| AUTH-03 ✱ | Система SHALL зберігати пароль лише як хеш із сіллю. |
| AUTH-04.1 | IF email має невалідний формат або вже використаний, THEN система SHALL відхилити реєстрацію. |
| AUTH-04.2 | IF `trainer_id` не рівно 9 цифр або вже використаний, THEN система SHALL відхилити реєстрацію. |
| AUTH-04.3 | IF password коротший за 8 або довший за 16 символів, або `trainer_name` коротший за 1 або довший за 30 символів, THEN система SHALL відхилити реєстрацію. |

## 2. Пошук і видача

| ID | Вимога |
| --- | --- |
| SRCH-01 ✱ | WHEN Guest/Player шукає умки, система SHALL повернути SharedUma, що задовольняють усі задані фільтри (AND): Umamusume, кожен із 5 статів (speed, stamina, power, guts, wit) ≥ мінімуму, `rank_id` = заданому (точний збіг), Factor. Фільтр, значення якого не задано, не обмежує видачу; «не задано» — відсутність значення (0 — це задане значення). |
| SRCH-02 | WHEN користувач задає кілька Umamusume, система SHALL повернути збіг із будь-якою з них (OR); WHEN задає кілька Factor — лише SharedUma з усіма заданими Factor (AND). |
| SRCH-03 ✱ | WHEN Guest/Player шукає картки, система SHALL повернути SharedCard за AND: SupportCard (збіг із будь-якою вибраною), `card_type` (одне значення), `rarity` (збіг із будь-яким вибраним), `level` ≥ мінімуму, `limit_break` ≥ мінімуму. |
| SRCH-04 ✱ | IF мінімум стата поза 0–2000, `level` поза 1–50, `limit_break` поза 0–4, значення фільтра нечислове або id довідника у фільтрі відсутній у довіднику, THEN система SHALL відхилити пошук. |
| RES-01 | WHILE власник запису має статус `flagged`, система SHALL NOT включати його записи до видачі. |
| RES-02 ✱ | Видача SHALL бути впорядкована: власники `verified` першими; далі за `created_at` запису за спаданням; за рівності — за id запису за спаданням. |
| RES-03.1 ✱ | Видача SHALL бути сторінками по 20 записів; сторінки нумеруються з 1. |
| RES-03.2 ✱ | WHEN запитано сторінку з номером, більшим за кількість сторінок (при ≥ 1 збігу), система SHALL повернути порожній список без повідомлення «Нічого не знайдено»; IF номер сторінки < 1, THEN система SHALL відхилити запит. |
| RES-04.1 | WHILE користувач неавторизований, відповідь сервера на пошук SHALL NOT містити `trainer_id`. |
| RES-04.2 | WHILE користувач неавторизований, інтерфейс SHALL NOT показувати `trainer_id`; WHILE авторизований — видача (відповідь і інтерфейс) SHALL містити `trainer_id`. |
| RES-05 ✱ | IF загальна кількість збігів дорівнює 0, THEN система SHALL показати «Нічого не знайдено» і, якщо задано хоча б один фільтр, «Спробуйте послабити фільтри». |

## 3. Рентал

| ID | Вимога |
| --- | --- |
| RENT-01 | WHEN Player виставляє умку (картку) з параметрами, що відповідають RENT-05.1–05.3, система SHALL створити SharedUma (SharedCard) і встановити `created_at` = `updated_at` = поточний час. |
| RENT-02 | IF Player уже має SharedUma (SharedCard), THEN система SHALL відхилити створення будь-якої іншої SharedUma (SharedCard) цього Player, незалежно від її параметрів; одна SharedUma і одна SharedCard одночасно дозволені. |
| RENT-03.1 ✱ | WHEN власник подає повний набір параметрів (SharedUma: Umamusume, 5 статів, `rank_id`, Factor; SharedCard: SupportCard, `level`, `limit_break`), система SHALL замінити всі параметри запису; IF набір неповний або запит подає не власник, THEN система SHALL відхилити його без змін. |
| RENT-03.2 | WHEN параметри замінено, система SHALL оновити `updated_at` і SHALL NOT змінювати `created_at`. |
| RENT-04 ✱ | WHEN власник знімає рентал, система SHALL не включати запис до жодної видачі, починаючи з наступного пошуку; уже отриманий результат не оновлюється. Спосіб збереження знятого запису (видалення чи деактивація) не визначено. |
| RENT-05.1 | IF стат поза 0–2000 або `rank_id` відсутній у довіднику Rank, THEN система SHALL відхилити створення/зміну SharedUma. |
| RENT-05.2 | IF `level` поза 1–50 або `limit_break` поза 0–4, THEN система SHALL відхилити створення/зміну SharedCard. |
| RENT-05.3 ✱ | IF Umamusume, SupportCard або Factor відсутні у довіднику, THEN система SHALL відхилити операцію без змін даних. |

## 4. Скарги

| ID | Вимога |
| --- | --- |
| REP-01 | WHEN Player подає скаргу, що не порушує REP-02, система SHALL в одній неподільній операції зберегти пару «скаржник — відповідач» і збільшити `reports_count` відповідача на 1. |
| REP-02 | IF скаржник уже скаржився на цього відповідача або скаржник = відповідач, THEN система SHALL відхилити скаргу без зміни `reports_count`. |
| REP-03 | WHEN скарга доводить `reports_count` відповідача до значення ≥ 5, Система SHALL у тій самій операції встановити йому `verification_status = flagged` незалежно від попереднього статусу (ADR-0006). |

## 5. Адміністратор

| ID | Вимога |
| --- | --- |
| ADM-01 | WHEN Admin подає запис довідника Umamusume, SupportCard, Factor або Rank, система SHALL створити запис. |
| ADM-02.1 ✱ | WHEN Admin верифікує Player зі `unverified`, система SHALL встановити `verified`; IF статус інший, THEN система SHALL відхилити дію без змін. |
| ADM-02.2 | Підставою верифікації SHALL бути скриншот. **[НЕПОКРИТА: у моделі немає ні поля, ні дії подання скриншота; сценарію немає.]** |
| ADM-03 | WHEN Admin відкриває список скарг, система SHALL показати для кожної скарги «скаржник» і «відповідач». |
| ADM-04 ✱ | WHEN Admin повертає Player зі `flagged`, система SHALL вимагати вибору `unverified` або `verified` (без вибору — відхилити), встановити вибраний статус, SHALL NOT змінювати `reports_count` і знову включити записи Player до видачі; IF Player не має `flagged`, THEN система SHALL відхилити дію (ADR-0008). |
| ADM-05 ✱ | IF користувач без `role = admin` (Player або Guest) виконує дію Admin (ADM-01, ADM-02.1, ADM-03, ADM-04), THEN система SHALL відхилити її без змін даних. |

## 6. Відкриті питання

1. Права Admin на пошук, рентал, скарги; чи має Admin `trainer_id`; чи можна зняти `verified` (ADR-0005, ADR-0007).
2. Результат автентифікації (сесія/токен), алгоритм хешування, формат email, регістр email; вихід, зміна профілю; тексти й спосіб показу помилок.
3. Поля видачі; що бачить Guest замість `trainer_id`; чи бачить Player свій запис.
4. Кількість Factor у SharedUma; зняття — видалення чи деактивація; чи може `flagged` змінювати рентал; часова зона `created_at`.
5. Причина й час скарги; чи може скаржитися Admin, на Admin, на `flagged`; відкликання скарги; сортування й порожній стан списку скарг (ADM-03).
6. Як акаунт отримує `role = admin`; редагування/видалення довідників, формат `icon`; подання скриншота (ADM-02.2); нефункціональні вимоги.
