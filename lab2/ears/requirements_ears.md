# EARS-вимоги: Umasearch

## 1. Облікові записи

| ID | Вимога |
| --- | --- |
| AUTH-01 | WHEN створюється Player, система SHALL записати `unverified`, `reports_count = 0`, `role = player`. |
| AUTH-02.1 | WHEN подано email і password існуючого запису, система SHALL автентифікувати користувача. |
| AUTH-02.2 | Система SHALL NOT приймати для входу інші ідентифікатори і SHALL NOT мати відновлення пароля. |
| AUTH-02.3 | IF пара не збігається, THEN система SHALL відхилити вхід, не вказуючи, яке поле хибне. |
| AUTH-03 | Система SHALL зберігати пароль лише як хеш із сіллю. |
| AUTH-04.1 | IF email має невалідний формат або вже використаний, THEN система SHALL відхилити реєстрацію. |
| AUTH-04.2 | IF `trainer_id` не рівно 9 цифр або вже використаний, THEN система SHALL відхилити реєстрацію. |
| AUTH-04.3 | IF password поза 8–16 символів або `trainer_name` поза 1–30, THEN система SHALL відхилити реєстрацію. |

## 2. Пошук і видача

| ID | Вимога |
| --- | --- |
| SRCH-01 | WHEN Guest/Player шукає умки, система SHALL повернути SharedUma, що задовольняють усі задані фільтри (AND): Umamusume, кожен із 5 статів ≥ мінімуму, `rank_id` = заданому, Factor. Незадані фільтри не обмежують видачу. |
| SRCH-02 | Кілька Umamusume — збіг із будь-якою (OR); кілька Factor — наявність усіх (AND). |
| SRCH-03 | WHEN Guest/Player шукає картки, система SHALL повернути SharedCard за AND: SupportCard (будь-яка з вибраних), `card_type`, `rarity` (будь-яке з вибраних), `level` ≥ мінімуму, `limit_break` ≥ мінімуму. |
| SRCH-04 | IF мінімум стата поза 0–2000, `level` поза 1–50 або `limit_break` поза 0–4, THEN система SHALL відхилити пошук. |
| RES-01 | Система SHALL NOT включати до видачі записи власників зі `flagged`. |
| RES-02 | Видача SHALL бути впорядкована: власники `verified` першими; далі за `created_at` запису за спаданням; за рівності — за id за спаданням. |
| RES-03 | Видача SHALL бути сторінками по 20; сторінка поза межами повертає порожній список. |
| RES-04 | WHILE користувач неавторизований, видача SHALL NOT містити `trainer_id` (ні в UI, ні у відповідях сервера); WHILE авторизований — SHALL містити. |
| RES-05 | IF видача порожня, THEN система SHALL показати «Нічого не знайдено» і, якщо задано фільтри, «Спробуйте послабити фільтри». |

## 3. Рентал

| ID | Вимога |
| --- | --- |
| RENT-01 | WHEN Player виставляє умку (картку) з коректними параметрами, система SHALL створити SharedUma (SharedCard) і встановити `created_at` = `updated_at` = поточний час. |
| RENT-02 | IF Player уже має SharedUma (SharedCard), THEN система SHALL відхилити створення другої такої самої; одна SharedUma і одна SharedCard одночасно дозволені. |
| RENT-03.1 | WHEN власник подає повний набір параметрів, система SHALL замінити всі параметри запису; неповний набір або не-власник — відхилити. |
| RENT-03.2 | WHEN параметри замінено, система SHALL оновити `updated_at` і SHALL NOT змінювати `created_at`. |
| RENT-04 | WHEN власник знімає рентал, система SHALL не включати запис до жодної видачі, починаючи з наступного пошуку. |
| RENT-05.1 | IF стат поза 0–2000 або `rank_id` відсутній у довіднику Rank, THEN система SHALL відхилити створення/зміну SharedUma. |
| RENT-05.2 | IF `level` поза 1–50 або `limit_break` поза 0–4, THEN система SHALL відхилити створення/зміну SharedCard. |
| RENT-05.3 | IF Umamusume, SupportCard або Factor відсутні у довіднику, THEN система SHALL відхилити операцію. |

## 4. Скарги

| ID | Вимога |
| --- | --- |
| REP-01 | WHEN Player подає допустиму скаргу, система SHALL в одній неподільній операції зберегти пару «скаржник — відповідач» і збільшити `reports_count` відповідача на 1. |
| REP-02 | IF скаржник уже скаржився на цього гравця або це той самий Player, THEN система SHALL відхилити скаргу без зміни `reports_count`. |
| REP-03 | WHEN `reports_count` відповідача стає ≥ 5, система SHALL у тій самій операції встановити `flagged` незалежно від попереднього статусу. |

## 5. Адміністратор

| ID | Вимога |
| --- | --- |
| ADM-01 | Система SHALL дозволяти Admin створювати записи в довідниках Umamusume, SupportCard, Factor, Rank. |
| ADM-02 | WHEN Admin верифікує Player зі `unverified`, система SHALL встановити `verified`; з іншого статусу — відхилити. |
| ADM-03 | Система SHALL показувати Admin список скарг із полями «скаржник» і «відповідач». |
| ADM-04 | WHEN Admin повертає Player зі `flagged`, система SHALL вимагати вибору `unverified` або `verified`, встановити його, скинути `reports_count` у 0 і знову включити записи до видачі; не-`flagged` Player — відхилити. **[NEEDS CLARIFICATION: скидання суперечить AC-03, а унікальність пари AC-12 не дає поскаржитися знову.]** |
| ADM-05 | IF користувач без `role = admin` виконує дію Admin, THEN система SHALL відхилити її без змін даних. |

## 6. Відкриті питання

1. Чи має Admin `trainer_id` (ADR-0005); права Admin на пошук, рентал, скарги; чи можна зняти `verified`.
2. Тексти й спосіб показу помилок; вихід, зміна профілю; регістр email.
3. Поля видачі; що бачить Guest замість `trainer_id`; чи бачить Player свій запис.
4. Кількість Factor у SharedUma; знімання — видалення чи деактивація; чи може `flagged` змінювати рентал.
5. Причина й час скарги відсутні; чи може скаржитися Admin, на Admin, на `flagged`; відкликання скарги.
6. Редагування/видалення довідників, формат `icon`; подання скриншота для верифікації; нефункціональні вимоги.
