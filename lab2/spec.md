# Специфікація акторів і головних цілей: Umasearch

**Дата**: 2026-10-21 .

**Статус**: Чернетка .

**Основа**: `spec.md` (розділи 1, 4, 5), `spec-addendum/spec-add-01…03`, ADR-0001…0005

## 1. Намір

Umasearch — вебсайт для гравців Umamusume: Pretty Derby. Користувач вибирає параметри умки або картки й отримує список підходящих гравців. Користувач також може виставити власну умку та картку в рентал.

## 2. Актори

| Актор | Хто це | Як зберігається |
| --- | --- | --- |
| Guest | Неавторизований відвідувач | Не зберігається |
| Player | Авторизований гравець; вхід лише за email + password | `Player.role = player` (значення за замовчуванням) |
| Admin | Модератор; вхід так само, як у Player | `Player.role = admin` (ADR-0005, статус Proposed) |

## 3. Головні цілі

| Актор | Головна ціль | Результат | AC |
| --- | --- | --- | --- |
| Guest | Знайти потрібну умку або картку | Список гравців без `trainer_id` | AC-10, AC-11 |
| Player | Знайти потрібну умку або картку | Список гравців із видимим `trainer_id` | AC-10, AC-11 |
| Player | Виставити власну умку та картку в рентал | Максимум 1 SharedUma і 1 SharedCard; рентал активний, доки власник його не зніме | AC-05, AC-09 |
| Player | Змінити або зняти свій рентал | Умка і картка змінюються повністю; `created_at` / `updated_at` ведуться автоматично | AC-09 |
| Player | Поскаржитися на іншого гравця | Одна скарга на гравця, не на себе; `reports_count` +1; при ≥ 5 статус `flagged` автоматично | AC-12 |
| Admin | Наповнювати довідники | Актуальні Umamusume, SupportCard, Factor, Rank | розділ 4 spec |
| Admin | Верифікувати `trainer_id` за скриншотом | Статус `verified`; верифіковані показуються першими у видачі | AC-11 |
| Admin | Переглядати скарги | Огляд скарг на гравців | AC-12 |
| Admin | Повертати гравців зі статусу `flagged` | Гравець знову потрапляє у видачу | AC-11 |

## 4. Правила пошуку (спільні для Guest і Player)

- Фільтри умки: Umamusume (мульти-вибір), мінімум кожного з 5 статів, rank, Factor (усі вибрані одночасно).
- Фільтри картки: SupportCard (мульти-вибір), card_type, rarity, мінімальні level і limit_break.
- Фільтри поєднуються через AND; мульти-вибір — збіг з будь-яким вибраним.
- Видача: без `flagged`; спочатку verified, потім за `created_at` спадаючи; по 20 на сторінку.
- Порожній результат: «Нічого не знайдено» і пропозиція послабити фільтри.

## 5. Розбіжності та неточності (не виправлялися)

1. **Реєстрація.** Реєстрація Guest як Player є очевидною ціллю, але в `spec.md` описано лише результат (AC-08: статуси за замовчуванням) і вхід. Окремої вимоги до реєстрації немає.
2. **Права Admin.** Розділ 4 не каже, чи може Admin шукати, виставляти рентал і скаржитися. ADR-0005 теж залишає це відкритим, статус `Proposed`.
3. **Скриншот для верифікації.** Admin верифікує за скриншотом, але ні в моделі, ні в цілях Player немає ні поля, ні дії для подання скриншота.
4. **Повернення зі `flagged`.** Вибір `unverified` / `verified` і скидання `reports_count` — припущення 1 у `spec.md`. Чи є це частиною цілі Admin, не підтверджено.
5. **Перегляд скарг.** Модель зберігає лише пару «скаржник — відповідач» (ADR-0002); причини й часу немає, тож зміст «перегляду скарг» для Admin не визначений.
6. **Видалення.** Правила видалення записів (крім зняття рентала власником) не визначені (припущення 4); хто може видаляти довідникові записи, що використовуються, невідомо.
